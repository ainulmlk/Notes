1. Déclarer une classe

à chaque nouveau "type d'objet" que le sujet te demande de représenter
public class NomClasse {
    // attributs, constructeur(s), méthodes
}
Nom de classe : toujours une majuscule au début (convention). public = visible partout ; sans rien = visible seulement dans le package.

2. Déclarer des attributs

ce sont les "données" que chaque objet doit connaître de lui-même
private String numeroSerie;
private int ram;
private ArrayList<Materiel> parc;
Convention : minuscule au début, puis une majuscule par mot (numeroSerie). Presque toujours en private : on encapsule, et on donne accès via des méthodes.

3. Les 4 niveaux de visibilité

à chaque attribut ou méthode — c'est le premier mot de la déclaration
private   // visible seulement dans SA classe
public    // visible de partout
protected // visible dans le package + dans les classes filles
             // (rien écrit) → visible seulement dans le package
Règle pratique : attributs presque toujours private, méthodes "utilitaires publiques" en public, ce qu'on veut garder accessible aux sous-classes en protected.

4. Constructeur(s) et this

à chaque fois qu'on doit pouvoir créer un objet — souvent 2 versions : un "vide" et un avec paramètres
public class Parc {
    private String nom;

    // constructeur sans paramètre
    public Parc() {
        this.nom = "";
    }

    // constructeur avec paramètre
    public Parc(String nom) {
        this.nom = nom;
    }
}
this = "l'objet en train d'être créé/utilisé". this.nom désigne l'attribut, nom tout court désigne le paramètre reçu : c'est pour ça qu'on écrit this.nom = nom; et pas nom = nom;.

5. Déclarer une méthode

chaque action que l'objet doit savoir faire
public String getNom() {
    return nom;
}

public void ajouterMateriel(Materiel m) {
    parc.add(m);
}
Forme générale : visibilité TypeDeRetour nomMethode(paramètres) { ... }. void = ne renvoie rien. Une méthode qui doit renvoyer un résultat se termine toujours par return.

6. Héritage : extends et super

quand plusieurs classes partagent des attributs/méthodes communs (ex: OrdiFixe et OrdiPortable partagent RAM/CPU)
public class MaterielInfo extends Materiel {
    private int ram;

    public MaterielInfo(String numeroSerie, int ram) {
        super(numeroSerie); // appelle le constructeur du parent, TOUJOURS en 1ère ligne
        this.ram = ram;
    }
}
Une classe fille récupère tout ce que possède le parent (relation "est-un": un OrdiFixe est un Materiel). Java n'autorise qu'un seul parent (héritage simple).

7. Redéfinir une méthode (@Override)

quand une sous-classe doit se comporter différemment du parent pour une même méthode
public class Switch extends MaterielReseau {
    private int nombrePorts;

    @Override
    public void afficher() {
        super.afficher(); // réutilise l'affichage du parent
        System.out.println("Ports : " + nombrePorts);
    }
}
Même nom + même signature que dans le parent = redéfinition. super.methode() permet d'appeler quand même la version du parent avant/après. C'est la base du polymorphisme : si on a une variable de type Materiel qui contient en réalité un Switch, c'est afficher() de Switch qui s'exécute.

8. Classe abstraite

pour empêcher de créer un objet "générique" quand seules les sous-classes ont un sens concret
public abstract class Materiel {
    // peut avoir des attributs, constructeur, méthodes normales
}
new Materiel(...) devient interdit (erreur de compilation) — seules les sous-classes concrètes (OrdiFixe, Switch...) peuvent être instanciées. Utile dès qu'un énoncé demande "on ne doit pas pouvoir créer un type général".

9. Interface

pour définir un "contrat" (des méthodes) sans dire comment il est rempli, souvent utilisé par plusieurs classes indépendantes
public interface Notificateur {
    void envoyer(String message);
}

public class NotificateurOutput implements Notificateur {
    @Override
    public void envoyer(String message) {
        System.out.println(message);
    }
}
Une interface ne contient que des entêtes (abstraites), jamais d'attributs, et est toujours public. Une classe peut implémenter plusieurs interfaces (contrairement à l'héritage) : class C extends A implements X1, X2.

10. Tableaux

nombre fixe d'éléments connu à l'avance
int[] notes;
notes = new int[10]; // 10 cases, indices 0 à 9
notes[0] = 15;
En pratique dans ce TD on préfère ArrayList (taille flexible) — le tableau reste utile pour un nombre fixe connu d'avance.

11. ArrayList + boucle for-each

liste de taille variable : LE cas du "parc de machines"
private ArrayList<Materiel> parc = new ArrayList<Materiel>();

parc.add(unMateriel);
parc.remove(unMateriel);

for (Materiel m : parc) {
    m.afficher();
}
ArrayList<Type> = généricité (section 15). Le for-each (for (Type v : collection)) parcourt chaque élément sans gérer d'indice.

12. if / while / for classiques

tests et boucles standard
if (condition) {
    ...
} else {
    ...
}

while (condition) {
    ...
}

for (int i = 0; i < 10; i++) {
    ...
}
break sort de la boucle, continue passe directement au tour suivant.

13. Exceptions : throws vs try/catch

dès qu'une opération peut échouer (fichier absent, etc. — typiquement la sauvegarde/chargement)
// remonter l'erreur à l'appelant :
public void sauvegarder(String fichier) throws IOException {
    ...
}

// attraper et traiter l'erreur ici :
try {
    parc.sauvegarder("parc.save");
} catch (IOException e) {
    System.out.println("Erreur : " + e.getMessage());
}
throws = "je ne gère pas l'erreur ici, c'est à celui qui m'appelle de le faire". try/catch = "je gère l'erreur ici et maintenant".

14. getClass() — connaître / comparer le type réel

rechercher tous les objets d'un type donné dans une liste hétérogène
for (Materiel m : parc) {
    if (m.getClass() == Switch.class) {
        resultat.add(m);
    }
}
getClass() vient de la classe Object (donc héritée par tout objet) et renvoie le type réel de l'objet, même s'il est manipulé via une variable de type parent.

15. Généricité

une classe qui doit pouvoir contenir "n'importe quel type", décidé au moment de l'utilisation
class Sac<T> {
    // T se comporte comme un type normal ici
}

Sac<Materiel> monSac = new Sac<Materiel>();
ArrayList<String> phrase = new ArrayList<String>();
Le <T> est remplacé par le vrai type au moment de la création (ArrayList<Materiel>, ArrayList<String>...).

16. Sauvegarde/chargement par sérialisation

"sauvegarder sur disque" / "recharger au démarrage"
public class Parc implements Serializable {
    ...
}

// sauvegarder
ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("parc.save"));
oos.writeObject(monParc);
oos.close();

// charger
ObjectInputStream ois = new ObjectInputStream(new FileInputStream("parc.save"));
Parc parc = (Parc) ois.readObject();
ois.close();
Il faut que toutes les classes stockées (Parc, Materiel et ses sous-classes) implémentent Serializable, sinon l'écriture échoue.

17. Pattern Singleton

garantir qu'une classe n'a qu'une seule instance dans tout le programme
public final class Singleton {
    private static Singleton instance = null;

    private Singleton() { } // constructeur privé : personne d'autre ne peut faire "new"

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
Constructeur private + méthode static qui crée l'objet une seule fois puis le renvoie à chaque appel.

18. Pattern Fabrique (Factory)

créer différents types d'objets selon la valeur d'un paramètre, sans que l'appelant écrive les "new" lui-même
public interface MaterielFactory {
    Materiel creerMateriel(String type);
}

public class MaterielFactoryImpl implements MaterielFactory {
    @Override
    public Materiel creerMateriel(String type) {
        switch (type) {
            case "switch": return new Switch(...);
            case "ordifixe": return new OrdiFixe(...);
            default: throw new RuntimeException("type inconnu");
        }
    }
}
Centralise tous les new à un seul endroit : pratique si le menu utilisateur doit créer un matériel selon le choix tapé.

19. Pattern Décorateur

ajouter des comportements à un objet de façon souple, sans multiplier les sous-classes
public interface Notificateur {
    void envoyer(String message);
}

public abstract class NotificateurDecorateur implements Notificateur {
    protected Notificateur objetDecore;

    public NotificateurDecorateur(Notificateur objetDecore) {
        this.objetDecore = objetDecore;
    }

    @Override
    public void envoyer(String message) {
        objetDecore.envoyer(message); // délègue à l'objet décoré
    }
}

public class LogNotificateur extends NotificateurDecorateur {
    public LogNotificateur(Notificateur objetDecore) { super(objetDecore); }

    @Override
    public void envoyer(String message) {
        super.envoyer(message);
        System.out.println("Log -> " + message);
    }
}
Le décorateur "enveloppe" un objet du même type (via une interface) et ajoute son propre comportement avant/après avoir délégué. On peut empiler plusieurs décorateurs : new EmailNotificateur(new LogNotificateur(base)).
